# Guide to expanding prediction research

This is a **future-work guide**, not a description of features already implemented or an authorization to change the application, database, permissions or production deployment. The existing [100 m model documentation](100m-models.md) describes the actual implementation and its limitations. The current model is exploratory, recognizes four tests and two 100 m targets, and does not use tempo data. It does not automatically incorporate new tests, events or training records.

The recommended sequence is to collect consistent observations, audit coverage, define an event-specific prediction question, build and evaluate a simple model, and only then consider a more complex model or application integration. Do not equate correlations with causal effects, or pooled differences between athletes with the effect of an individual athlete improving.

## Preparation for the coming season

1. Agree with the coach on a practical, repeatable set of tests, protocols, units, timing methods and footwear. Record actual test dates, values and same-day attempts consistently. Do not require every athlete to complete every test: record what actually happened and keep missing values missing.
2. Record or import eligible competition results with the correct athlete, event, date, unit, outdoor/indoor classification and available wind. Review uncertain classifications rather than assuming them. Preserve nonnumeric marks as such. Note that the application may permit corrections after the event.
3. Record tempo participation and each segment's actual execution status, time and spikes where available. Preserve distances and rest as recorded in the plan; do not enter a planned result as a measured result. Do not infer a missed session from absence of a record.
4. Repeat measurements over time, including across seasons, and capture subsequent competitions for the same athletes when naturally available. Where practical, document when a result became available or was corrected. A performance date alone cannot establish what was known at an earlier forecast date.
5. Before modelling, review counts of distinct athletes, sessions, test dates, event results and usable future outcomes. Dates and reused race results are not independent observations. Protect any athlete-level exports and model artifacts; use the existing read-only connection and approved access procedures.

This plan does not impose a testing frequency, invent mandatory fields or change coaching practice. Protocols, recording practices and any changes to the application or schema require agreement with the project owner.

## Add a test

### What to review first

The goal is to **consider every test**, not to force every test into one model. For each candidate, identify its stable ID, name, unit, category, direction, protocol and any changes in measurement method over time. Do not merge distinct tests just because they have similar names or units. A current test definition may have changed since older results were recorded; investigate comparability rather than silently treating all values as equivalent.

From `ml\`, the existing 100 m-only studies can help review the data:

```powershell
.\.venv\Scripts\python.exe scripts\analyze_data.py
.\.venv\Scripts\python.exe scripts\correlate_tests_100m.py --event-id 1 --confirmed-unknown-outdoor-ids reports\100m_readiness_20261124T171700749006Z\confirmed_outdoor_result_ids.csv
.\.venv\Scripts\python.exe scripts\analyze_100m_changes.py --event-id 1 --confirmed-unknown-outdoor-ids reports\100m_readiness_20261124T171700749006Z\confirmed_outdoor_result_ids.csv
```

Use your own reviewed confirmation file, not a copied placeholder. These scripts require the documented read-only connection and use a current snapshot. The audit describes all tests and competition coverage; the correlation study uses the 100 m next-30-day outcome and latest strictly prior test; the change study describes individual changes under its own pairing rules. None automatically adds a feature to a saved model. Review the report definitions before interpreting counts, input age and correlations. A correlation may reflect differences between athletes, repeated records, age, training or selection into competitions, and is not an individual improvement coefficient.

For each target and test, report usable prediction dates, distinct athletes, independent test and outcome IDs, input ages, missingness and repeated same-athlete test/outcome pairs. Distinguish no recorded race from a poor result. Agree on any age cutoff or test-protocol mapping before applying it. If data are too sparse, retain the test in the audit and collect more rather than inventing a coefficient.

### Implementation steps when approved

1. **Define the input contract:** reviewed test ID, exact meaning, unit, direction, latest strictly prior date, same-day attempt selection and invalid-data handling. Keep test IDs stable for lineage; use a stable feature key. Never use athlete names as model features.
2. **Update the feature pipeline and metadata validation.** Today the four definitions are hard-coded in `src\tfhub_ml\analysis\multi_test_study.py` (`TESTS` and `build_feature_examples`), and training and inference in `src\tfhub_ml\analysis\saved_models.py` import that same mapping. Test the metadata mismatch, missing, invalid, same-day and historical date cases. If test selection changes, update the research analyses and their tests as appropriate; do not silently change old study definitions.
3. **Choose a bounded candidate strategy before looking at held-out results.** The current code enumerates every nonempty subset. With 18 tests that is 262,143 subsets *per target*, impractical and especially prone to overfitting. Start with individually reviewed candidates and a small set of justified combinations, or investigate a missing-aware approach when there are enough data. Do not assume more features improve accuracy. Define explicit behavior for unavailable combinations; never replace missing values with zero without a justified, tested method.
4. **Train and validate without leakage.** For a held-out date, fit preprocessing, selection and coefficients only on training data whose outcome windows have fully matured, excluding the held-out athlete for the current generalization question. Compare against a baseline and the existing model on identical evaluable cases. Report skipped cases, distinct athletes, repeated windows, athlete-weighted as well as example-weighted errors, and cases without prior race history. When enough data exist, separately study within-athlete changes and future seasons; do not interpret an across-athlete slope as a within-athlete effect.
5. **Version the model contract.** The present JSON loader and predictor depend on the current global `TESTS` order and keys. Simply editing that mapping can break or misinterpret old artifacts. Introduce a versioned, validated feature registry and compatible loader or explicit migration before changing the contract; preserve old code and artifacts. Record the test definition, preprocessing, training cutoff, code revision, environment, training counts, evaluation and unavailable subsets. Do not overwrite an existing artifact.
6. **Test and document the full path:** extraction, subset selection, serialization and load round-trip, prediction, unavailable inputs and metadata changes. Retrain into a new private, ignored artifact only after review. The current model does not train itself when a test is added or an athlete result is edited.

The current minimum of more distinct athletes than coefficients and full rank is only a mathematical guard, not a validated sample-size threshold. More robust feature selection and model types must be evaluated using independent data, not selected merely because the training error is smaller.

## Add a competition event

Each event needs a separately defined and evaluated prediction problem. **Passing another ID to the current 100 m training command will not work**: `src\tfhub_ml\analysis\sprint_readiness.py` verifies the event name `100 m` and unit `s`, and `near_term_100m.py`, `within_athlete.py`, `saved_models.py` and their scripts contain 100 m-specific target, date or direction assumptions. The existing 60 m season feasibility and experimental scripts are separate research examples, not a generic event system.

1. **Review the event catalog and records.** Identify the verified competition event ID, exact event definition, unit, individual versus relay context, athlete linkage, numeric and nonnumeric marks, number of athletes and seasons, missingness, wind where relevant and `OUTDOOR`/`INDOOR`/`UNKNOWN` coverage. Use the existing general audit first; review IDs in the target database because IDs are not necessarily portable.
2. **Agree on the target with the coach.** Specify the exact event, recorded mark and units, whether lower or higher is better, eligible classifications and conditions, prediction date, forecast horizon, season boundaries, best-of-season rule and whether an already known mark participates. Do not assume a 100 m season or its fastest-time logic works for jumps, throws, indoor events or relays. Define treatment of same-day ordering, ties, unknown classifications, invalid marks and no observed outcome. Do not assume a future event's unknown records are covered by the 100 m confirmation file.
3. **Build an event-specific readiness audit and examples.** Verify metadata and exact reviewed classifications, use only features available before prediction, and separate missing results from bad performance. Include calendar-complete windows, outcomes and counts by athlete and season. Obtain explicit confirmation for specific uncertain records only where appropriate. Preserve event IDs and units in the model contract.
4. **Compare simple baselines and candidate inputs.** Choose baselines appropriate to that event and direction, such as a prior event mark when available or a training-fold mean. Compare test-enhanced models against each baseline on matched cases; keep a no-prior-mark cohort separate. Judge each event independently: the 100 m weights and errors are not transferable evidence for 200 m or another event.
5. **Implement and test event-specific training and prediction.** Extract general helpers only where semantics genuinely match; parameterize or replace 100 m checks intentionally rather than removing validation. Add cases for direction, units, season/horizon boundaries, same-day marks, classification, nonnumeric results, empty outcomes, metadata mismatch and historical availability. Version the artifact schema with event, target and direction; avoid loading 100 m artifacts as another event.
6. **Evaluate future seasons and hold out athletes** as appropriate to the intended use, with completed outcomes and training-only preprocessing. Record counts and skipped folds, compare matched cohorts, and retain a separate protected artifact per event and target. Do not claim valid uncertainty ranges without enough independent calibration data.

The local predictor currently accepts `prediction_seconds` and applies a minimum for a known season best; it is specifically for the documented 100 m targets. A higher-is-better event requires a new explicit contract and appropriate direction-aware behavior, not a renamed seconds field.

## Extend with tempo training

### What TFHub currently records

The authoritative schema and rules are in [`training-module-design.md`](../../docs/backend/training-module-design.md), [UC-510](../../docs/backend/use-cases/UC-510-TRN-complete-training.md) and [UC-511](../../docs/backend/use-cases/UC-511-TRN-athlete-training-history.md). The ML extractor currently reads **no tempo tables**, and the existing reader grants do not cover them.

| Source | Relevant information | Interpretation |
| --- | --- | --- |
| `training_sessions` | `id`, `training_date`, `training_type`, `status` | Session date can be null for planned sessions; only `TEMPO` has this execution structure. `COMPLETED` does not mean every execution has a result. |
| `training_definitions` | `id`, `training_session_id` | A session may have several plan variants. |
| `training_segments` | `id`, `training_definition_id`, `sequence_number`, `distance_m`, `rest_after_seconds` | Planned distance in metres and optional planned rest in seconds, not proof of actual rest or completed work. |
| `training_athlete_participations` | `id`, `athlete_id`, `training_session_id`, `training_definition_id` | Links the individual athlete to a variant. Historical participation remains meaningful after a group change. |
| `training_segment_executions` | `id`, `participation_id`, `training_segment_id`, `training_definition_id`, `status`, `measured_result`, `uses_spikes` | Measured running time is seconds when `RECORDED`; other statuses have no time. `uses_spikes` is independent of status. |

`RECORDED` requires a nonnegative time; **zero is valid in the application**. Do not silently change it or call it invalid application data. A future speed calculation must avoid division by zero and explicitly report and review zero-time records separately. `PENDING`, `COMPLETED_WITHOUT_RESULT` and `NOT_COMPLETED` are distinct and must not become zero times. `FREE_TEXT` has no tempo participation or execution records. Session plans and executions can be corrected; UC-511 states that history reflects the current persisted structure, not an immutable snapshot. Sessions can also be deleted, so missing history does not prove a session never occurred.

### Recommended development steps

1. **Agree on the research question and access.** Decide whether tempo is intended to improve next-30-day form, season best, or both, and what timing and feature windows the coach considers meaningful. Inspect actual data coverage first. Before connecting, have an administrator review the minimum columns and grant only necessary read access to the existing dedicated role through the approved manual process. Do not grant writes, change Compose or expose PostgreSQL. Do not modify the existing grant script or assume the current role already has these permissions.
2. **Extend read-only extraction.** Add separate, explicitly typed tempo data to the existing `REPEATABLE READ READ ONLY` snapshot in `src\tfhub_ml\data\extract.py`, preserving IDs and linking execution -> participation -> session and execution -> segment -> definition. Enforce that session/definition IDs match across those paths; use stable IDs rather than sequence as identity, and retain execution status. Exclude undated sessions from temporal examples and report them separately. Avoid names and unrelated staff notes. Add isolated tests and check permissions failures explicitly.
3. **Audit before engineering features.** Report dated sessions, athletes, definitions and segment executions, status counts, missing results, zero recorded times, distances, planned rest, spikes, data ages and coverage against eligible future event outcomes. Count distinct athletes and sessions, not only segment rows. Treat missing participation, pending executions and incomplete sessions as unknown, not as evidence the athlete did not train or ran slowly.
4. **Specify candidate features with units and provenance.** Examples to discuss—not approved defaults—include elapsed days since a recorded session, number of recorded segments at a particular distance, or summary time/speed for comparable distance and footwear over an explicitly chosen prior window. Speed in m/s can only be calculated for positive measured seconds; report zero separately. A total distance based on recorded segments is not necessarily the total distance actually run. Do not combine different distances, rest protocols or spikes without an explicit definition and validation. Planned rest is not measured recovery, and a session's aggregate cannot assume all planned segments were performed.
5. **Construct features at each forecast date using prior information only.** Include dated sessions strictly before the prediction date unless a different same-day ordering rule is explicitly approved. Use only execution information demonstrably available by then; a session date is not its entry or correction timestamp. If historical availability cannot be proven, label the evaluation retrospective and qualified. Freeze window boundaries, handling of incomplete sessions, zero and missing values, spike distinctions and aggregation rules before evaluating outcomes. Never use future executions or compute feature thresholds on all data.
6. **Compare on matched cases.** Evaluate a test-only baseline against test-plus-tempo candidates on the same held-out prediction dates and athletes, using training-only preprocessing and fully matured outcome windows. Also report how many athletes and dates lack tempo data and how their predictions are handled. Track overlapping sessions and reused races; distinguish within-athlete change evidence from pooled correlation. Report no-race windows, skipped folds and both athlete- and date-weighted error.
7. **Version and verify.** Store feature definitions, units, time windows, status rules, source provenance and preprocessing in a new versioned artifact. Add tests for multi-definition joins, group changes, zero time, each execution status, partial and undated sessions, no participation, repeated segments, corrections, same-day/future exclusion and serialization. A tempo feature does not exist until extraction, training, inference and evaluation all agree on its contract.

Current use-case rules permit corrections after completion, but do not themselves establish an immutable as-of history for ML. If reliable historical entry/correction times or immutable snapshots are needed, investigate the actual data and propose a separate architecture/data-model change for owner approval; do not invent schema fields or use Hibernate schema updates.

## Before application use

The future athlete-page experience will need its own approved requirements, authorization and architecture: data access respecting the athlete scope, a versioned model selection policy, update/recomputation behavior, handling for insufficient or stale inputs, monitoring, privacy and calibrated uncertainty. Evaluation for new athletes, existing athletes and future seasons should be distinguished. The current tools print local experimental point estimates and do not provide an API, deployable inference service, automatic updates, validated season model or prediction ranges.
